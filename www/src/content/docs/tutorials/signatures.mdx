Its caller may choose a split without owning a key. Here you add an authority
requirement: the puzzle returns a condition, and the spend bundle must supply
the corresponding signature. The private key is never a puzzle argument.

An amount guard or caller-controlled boolean does not establish ownership. The
signature-payment fixture returns an `AGG_SIG_ME` condition for a fixed public
key, asserts the input amount, and creates the fixed recipient coin.

## The signed message is not the whole signature context

`agg_sig_me(OWNER, message)` names the signature requirement. Its serialized
condition uses opcode 50 and includes a public key and a message. The consensus engine binds
that message to the spent coin's ID and the network signature domain. A valid
signature for one coin must not authorize a different otherwise identical coin.

The message is a `Message32` argument and therefore one atom of exactly 32 bytes.
Its correct shape does not mean the application chose the right message
commitment. This fixture fixes the payment policy, so selecting another message
does not change the recipient or amount. More flexible delegated policies need
an explicit commitment to the authorized action.

## Test the aggregate signature

Plain CLVM execution only returns the signature condition. The ledger suite
submits a missing aggregate signature and requires rejection with rollback,
then signs with the expected key and checks the exact payment. The simulator
infrastructure also tests reuse against a different coin.

The puzzle bodies refer to named `OWNER`, `FIRST_SIGNER`, and `SECOND_SIGNER`
values. Their actual public-key bytes live in `puzzles/fixture_keys.rs`,
available in the supporting-source drawer beneath each comparison. Moving them
out of the body changes presentation, not the need to review the correct key.

The fixture keys come from public deterministic seeds `[0x17; 32]` and
`[0x18; 32]`. Reproduce their public values with:

```sh
cargo run -p chialisp-oxide-simulator --example fixture-keys --locked
```

These keys are intentionally public and must never control real funds.

## Try the puzzle without confusing a condition with a signature

After the [quickstart](/chialisp-oxide/start/quickstart/), run the linked native
fixture with the manifest's 32-byte message:

```sh
target/debug/chialisp-oxide native signature-payment --solution '(0xabababababababababababababababababababababababababababababababab)'
```

The accepted result includes a signature **requirement**; this command has not
signed anything. Follow [the selected-export walkthrough](/chialisp-oxide/reference/cli/#execute-a-selected-export)
with `chialisp_oxide_puzzles::signature_payment::puzzle` and that solution to
inspect the compiled CLVM result too. A VM run can succeed even when a spend
bundle without the required signature would be rejected. The ledger scenarios
in the lab check that additional boundary.

## Require both signatures

The two-signature fixture emits two `AGG_SIG_ME` conditions. The aggregate
signature must satisfy both keys; this is an explicit two-of-two policy, not a
general threshold-signature implementation.

two-key spend. Read the complete cases in the
