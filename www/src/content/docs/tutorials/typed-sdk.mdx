A recipient puzzle hash and a spent coin ID are both 32-byte values, but
passing one where the other is required can encode the wrong policy. Amounts
and timestamps also share a numeric representation without being interchangeable.
The SDK uses Rust's nominal types to reject these direct API mixups before
CLVM generation.

## Start with an ordinary Cargo library

The working consumer is `examples/cargo-puzzles`. Its local `[workspace]`
keeps it independent of the compiler workspace. `oxide-sdk` and its marker
macro are actual crates; neither is published to crates.io.

<CargoSource file="manifest" />

A separate checkout can use a path dependency or a Git dependency pinned to a
reviewed full commit of this repository. Do not substitute an invented registry
version. The [quickstart](/chialisp-oxide/start/quickstart/) installs the pinned
nightly components and makes the `cargo oxide` command available.

## Mark the functions to compile

<CargoSource file="library" />

`#[oxide_sdk::puzzle]` marks an export and preserves its Rust function body.
The macro does not translate the function into another language. Rust checks
the source normally; the driver then lowers each marked function's supported
reachable code through the typed IR and Rue backend.

`pay` requires an `Amount`, checks `PAYMENT_CAP` with `.is_at_most`, and emits
`ASSERT_MY_AMOUNT 1000` and a fixed-destination `CREATE_COIN`. Its amount choice
is permissionless and an unpaid remainder becomes a fee. `guarded_add` is a
second export with primitive `u64` arguments; its numeric result is not a list
of spend conditions and it is not a coin puzzle.

The unannotated `native_description` uses references, allocation, formatting,
and iteration. It remains native-only because neither export calls it. If an
export reaches unsupported code, extraction rejects it; the marker does not
make arbitrary Rust compilable to CLVM.

## Let Cargo supply features and generated code

<CargoSource file="build" />

This build script runs as an ordinary host program with `std`. It writes
`PAYMENT_LIMIT` under Cargo's `OUT_DIR`, and `include!` brings that generated
Rust into the library. The default limit is 1,000; `strict-cap` changes it to
100. Input 101 therefore distinguishes the configurations. Compiling the
library as an isolated source file would lose this Cargo-provided environment.

Run the normal native checks from the repository root:

```sh
cargo check --manifest-path examples/cargo-puzzles/Cargo.toml --locked
cargo test --manifest-path examples/cargo-puzzles/Cargo.toml --locked
cargo test --manifest-path examples/cargo-puzzles/Cargo.toml --locked --features strict-cap
```

Then check the supported CLVM subset and compile the exports:

```sh
cargo oxide check --manifest-path examples/cargo-puzzles/Cargo.toml --locked
cargo oxide build --manifest-path examples/cargo-puzzles/Cargo.toml --locked
cargo oxide build --manifest-path examples/cargo-puzzles/Cargo.toml --locked --features strict-cap
```

`check` does not publish an artifact bundle. A successful `build` writes an
immutable bundle under this consumer workspace's `target/oxide/artifacts/`;
`latest.json` points to its manifest and each export's artifacts. Inspect the
manifest rather than assuming a generated filename. Failed builds preserve
the previous successful bundle.

Native tests establish native behavior. The Cargo integration regressions also
execute the generated payment conditions and arithmetic in both optimizer
modes, including the changed feature cap. The registered Cargo corpus adds
independent Chialisp comparisons and puzzle-specific ledger scenarios.

## Observe a typed API failure

`examples/cargo-invalid` uses the same real SDK dependency. With its
`type-error` feature, a marked function passes `CoinId` to `create_coin`, which
requires `PuzzleHash`. This command intentionally fails with Rust `E0308`:

```sh
cargo check --manifest-path examples/cargo-invalid/Cargo.toml --locked --features type-error
```

Without that feature, its division example passes native tests but
`cargo oxide check` rejects the unsupported operation. Valid Rust and accepted
CLVM-source Rust are separate checks.

The standalone driver regressions below also exercise both domain mistakes.
Their observed diagnostics require the two type names and no emitted IR:

<DomainErrorExamples />

```sh
cargo test -p oxide-driver --test newtypes --locked
```

These protections apply at typed helper call sites. Rue's nominal struct types
can express analogous distinctions; this is not unique to Rust.

## Name units and policy before constructing conditions

The actual consumer source above defines `COIN_AMOUNT` and `PAYMENT_CAP` with
`Amount::from_mojos` and gives the fixed `PuzzleHash` a `RECIPIENT` name.
`PaymentConditions` names the return layout. These names make the policy
readable without requiring a reader to decode condition numbers or tuple fields.

Use `.mojos()` when checked arithmetic needs the inner integer, then construct
the result with `Amount::from_mojos`. For time, use
`Timestamp::from_unix_seconds` and `.unix_seconds()`: those names mean an
absolute Unix timestamp, not a delay since coin creation. The
[split-payment](/chialisp-oxide/tutorials/split-payment/) and
[recovery](/chialisp-oxide/tutorials/recovery/) examples exercise these methods.

The helpers keep numeric condition discriminants in the SDK's `opcode` module.
The [condition reference](/chialisp-oxide/reference/conditions/) explains the
serialized form. These remain plain Rust functions and type aliases, not a
builder backed by heap allocation or an alternative puzzle language.
The repository's [readability design notes](https://github.com/judeallred/chialisp-oxide/blob/main/docs/readability.md)
record the API rationale and the before/after validation method.

## Inspect the shared SDK definitions

The consumer and corpus packages use this ordinary source through the real
`oxide-sdk` dependency. The crate also re-exports the puzzle marker macro.
Standalone frontend regression fixtures reach the same definitions through
`sdk/oxide.rs`; that compatibility path is not used to build the corpus.

<SdkSource />

`PuzzleHash`, `CoinId`, `PublicKey`, and `Message32` wrap fixed-size bytes.
`Amount` and `Timestamp` wrap `u64`. Named helpers supply four condition codes;
their result aliases remain tuples, so callers can still construct raw tuples
or incorrect opcodes manually.

These small values implement `Copy` and `Clone` in Rust. Implicit `Copy` reuse
of an amount, recipient, or key is supported on-chain; explicit `.clone()` calls
are not, because their borrowed receiver and trait dispatch are unsupported.
The fields are public:
`PuzzleHash(coin.0)` explicitly unwraps and rewraps bytes
and bypasses the direct source-level distinction. Amounts also remain ordinary
duplicable numeric values: an inner `u64` can be copied and wrapped again.
Move checking does not enforce money conservation or prevent double spends.

## Keep policy checks explicit

ABI decoding does not call a wrapper constructor or custom validator. A
`PuzzleHash` argument receives an atom of exactly 32 bytes, not proof that the
bytes identify the intended puzzle. An `Amount` receives a canonical in-range
integer, not an application cap or conservation invariant. An attacker can
supply any correctly sized bytes at the wire boundary.

The accepted wrapper form is deliberately narrow: local or vetted SDK,
nongeneric, non-macro-generated `#[repr(transparent)]` structs with exactly one
supported nonzero-size field and no custom `Drop`. Nested supported wrappers
erase recursively. General structs, enums, additional zero-size fields, and
arbitrary dependency types remain unsupported.

The feature regressions reject unsupported layouts, preserve the byte ABI,
exercise malformed solutions in both optimizer modes, and compare helper
outputs with independent Chialisp. These checks do not establish authorization
or eliminate policy mistakes. Keep destination, signatures, replay protection,
fees, and coin-context requirements explicit in the puzzle and ledger tests.
