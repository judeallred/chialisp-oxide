**WIP prototype. Not ready for use with funds or production puzzles.**

A password comparison needs a trusted expected hash. If a spender supplies both
the password and its expected hash, the comparison establishes no authority:
anyone can choose a new matching pair.

The [original first smart coin lesson](https://github.com/Chia-Network/chialisp-web/blob/dcf06c14836c7ad3f486a5bea36c5a812fd9a5e8/docs/chialisp-primer/first-smart-coin.md#L21-L40)
separates two objects. A reusable module checks a hash and returns the requested
conditions. A particular coin commits to an instance of that module with the
expected hash already bound. That binding is called **currying**.

This lesson preserves that distinction and the original example's insecurity:
the password becomes public in a spend, and its conditions are unsigned.

## Read the reusable module

<SourceComparison slug="password-coin" />

The module selects the first three fields of its environment:

```text
(expected_hash password conditions . ignored_tail)
```

It hashes the password's exact atom bytes, compares the resulting digest with
the expected hash, and returns the conditions unchanged when they match.
It inspects the conditions field only on that successful branch.

The Rust port uses ordinary enum matching, byte hashing and slice equality.
The raw environment is deliberate: the original accepts arbitrary atom bytes,
arbitrary condition trees and an uninspected final tail. Replacing its fields
with a fixed argument tuple or a typed payment constructor would change the
module's accepted inputs.

Keep the byte contract visible:

- An empty password, `0x00` and `0x0000` are different messages. No integer or
  text conversion runs before hashing.
- A digest has 32 bytes. A leading zero remains part of the comparison.
- A pair in either hash or password position cannot satisfy the atom comparison.
- Matching passwords pass the selected condition tree through unchanged. A
  successful VM result does not establish that the conditions describe a valid
  spend.
- Extra fields and improper tails after the third field are ignored.

The Chialisp source is the original module span, without a new wrapper. Its
measured compiled size is 31 bytes. Rust and Rue have separately compiled
artifacts and their own hashes; equal results do not imply equal module identity.

## Bind the expected hash before creating the coin

Write `M` for the compiled module and `H` for `SHA256(password_bytes)`. A
standard one-argument curried instance has this CLVM structure:

```text
(a (q . M) (c (q . H) 1))
```

`q` quotes a value, `c` constructs a pair, and `a` applies a program to an
environment. The `1` selects the spender's complete solution. Applying this
instance to `(password conditions . tail)` therefore applies `M` to
`(H password conditions . tail)`.

The sequence matters:

1. Compile the module and construct an instance that embeds `H`.
2. Compute the **instance's** tree hash and use that hash in the coin.
3. Reveal that same instance when spending, with the password and conditions
   in its solution.

The coin's committed puzzle hash constrains the reveal. A different instance
can pass its own password test and still fail consensus with `WrongPuzzleHash`
when submitted for this coin. A module hash and a curried instance hash identify
different programs.

Use each build's own instance. Binding the same `H` to different Rust, Chialisp
or Rue module bytes does not make their instance hashes interchangeable.

The validation harness constructs fixed public test instances. It independently
checks the standard curry tree, serialized bytes, tree hashes and the relation
between raw and curried execution. The general typed instance-authoring workflow
remains on the [project roadmap](https://github.com/judeallred/chialisp-oxide/blob/main/docs/roadmap.md).

## Demonstrate the remaining policy error

Currying binds the expected hash. It does not bind the destination requested in
the output conditions.

The complete-spend experiment uses the same coin and initial simulator state
in two separate runs. One submits the intended destination. The other retains
the revealed password and substitutes another destination. Both spends succeed.
This demonstrates the original lesson's unsigned-condition weakness; the Rust
compiler accepts the program because the policy itself permits that behavior.

Rust's representation checks are useful, but they do not establish who should
be authorized or what that authority should cover. Compare this example with
[typed payment and signature conditions](/chialisp-oxide/tutorials/typed-sdk/)
and [errors the compiler can prevent](/chialisp-oxide/verification/error-study/).

## Inspect the evidence and its limits

The [laboratory comparison](/chialisp-oxide/lab/password-coin/) contains
{passwordPuzzle?.cases.length} named and
{format(passwordPuzzle?.generated_cases ?? 0)} generated module inputs. Native
execution calls the actual Cargo export. Rust and Rue each run with optimization
off and on, alongside independently compiled Chialisp. An independent Python
relation hashes raw password bytes and checks exact condition-tree outputs.

Curried-instance evidence is separate from the uncurried module comparisons.
It retains each reveal, instance identity, solution, VM result and ledger
observation. The raw module alone receives no password-locked spend credit.

There is also a classification limit worth inspecting. A wrong password produces
a typed program failure in the execution VM. The simulator's consensus layer
reports the broader `GeneratorRuntimeError`, which can represent several kinds
of runtime failure. The harness records that observation and rollback separately;
it does not count that umbrella code as a specific semantic consensus rejection.

Low-budget experiments are separate too. For example, a large password can
exhaust a budget before a later field is inspected. Different compilation and
optimization choices have different costs. Resource exhaustion is inconclusive,
and agreement on ordinary outputs does not establish equal cost thresholds.

The performance gap is substantial. The optimized Rust module is
{format(passwordRust?.bytes ?? 0)} bytes, compared with
{format(passwordChialisp?.bytes ?? 0)} for Chialisp and
{format(passwordRue?.bytes ?? 0)} for optimized Rue. The named valid curried
spend costs {format(passwordSampleCost('rust_mir'))} VM units in optimized Rust,
{format(passwordSampleCost('chialisp'))} in Chialisp, and
{format(passwordSampleCost('rue_source'))} in optimized Rue. These measured
examples are a reason to improve the compiler; they are not general cost
guarantees, and exclude overall consensus condition and bundle costs.

The current formal models reject SHA. These checks do not prove cryptographic
security, compiler preservation or the safety of a password-based coin policy.
The successful destination-retargeting experiment supplies a concrete reason
to keep this example as a lesson rather than use it with funds.

## Reproduce the experiment

From the repository root, use the pinned Rust toolchain and locked dependencies:

```sh
cargo build --workspace --locked
cargo test -p chialisp-oxide-corpus password::tests --locked
target/debug/chialisp-oxide validate --output corpus/validation.json
python3 scripts/check-password-coin.py --self-test --replay
```

The validation command runs all Cargo puzzles and submits the password-instance
transactions to the simulator. The Python command checks current source and
evidence, challenges its independent relation with corruptions, and executes
the retained serialized programs. That replay checks the primary VM results;
it does not submit the transactions again. Run the complete validation command
when changing a puzzle or the instance constructor.
