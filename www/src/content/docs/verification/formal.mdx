The formal companion works on typed scalar expressions in the actual
source-derived IR. Independently written specifications describe the intended
counter policy. Z3 looks for a violating input; its statuses and replay
evidence are recorded rather than translated into a blanket security claim.

<FormalEvidence />

## What is specified

For `bounded-counter`, the range obligation says that every successful result
is between 1 and 1,000 and equals the input plus one. The acceptance obligation
says that, for a successfully decoded typed `u64`, execution succeeds exactly
when input is below 1,000.

The report includes source, original/mutant IR, specification, and SMT query
hashes so the model and obligations can be tied to the specific compiled
fixture. The site verifies those files before building. A satisfying input demonstrates nonvacuity: the
property is not “proved” merely because every input rejects. That witness is
replayed in native Rust and both CLVM optimization modes.

## Show that a broken guard is caught

The mutation removes only the outer `counter < 1000` assertion and retains
checked increment. The solver must produce a counterexample to the range
specification. The original native function and both original CLVM programs
must reject it; both mutated CLVM programs must accept the now-out-of-policy
result.

This connects a model-level finding to executed artifacts. Witness replay is
still test evidence, not a universal compiler-preservation theorem.

Replay rejection has typed failure evidence. The scalar assertion witness must
report `{kind: "program", code: "raise"}`; a matching diagnostic string does not
count. Tree projections can reject with other program codes. A cost, allocator
or VM stack limit is a resource failure, and serialization/internal errors are
infrastructure failures. Both categories abort proof replay instead of becoming
rejection witnesses. The current report gates reject missing, unknown or
inconsistent metadata, including inside mutation and optimization controls.

The shared classifier and wire protocol, plus the replay gate helpers, are
hashed evidence inputs. These checks bind recorded executions to their failure
interpretation; they do not prove VM semantics or resource equivalence.

The earlier hand-authored capped-payment integer-policy experiment is separate:

## A separate structural tree model

The [p2_conditions factory](/chialisp-oxide/tutorials/p2-conditions/) adds a
separate model over arbitrary finite atom/pair trees. Atom contents are byte
sequences, rather than integers; leading zeros and improper tails are preserved.
The independent specification requires acceptance exactly for pair environments
and output `(1 . first(environment))`. Its domains include both atoms and pairs,
with nonvacuity checks and mutation counterexamples replayed in the VM.

```sh
python3 scripts/check-tree-proofs.py --output corpus/tree-proofs.json
```

The [structural report](/chialisp-oxide/reports/tree-proofs.json) includes its
source-derived IR, independent specification, SMT queries, and replay evidence.
This is an IR-model proof, not a theorem about all compiled Rust. Recursive
data in this model is separate from the frontend's
[recursive Rust call support](/chialisp-oxide/tutorials/recursive-trees/).
Both current models reject all version-4 runtime programs, including unused
functions and runtime nodes in dead branches. Finite VM replay does not prove
termination; resource failures abort replay rather than count as rejection.
Runtime allocation and general program evaluation remain unsupported. The scalar verifier rejects
tree expressions, including expressions in unchosen branches, instead of
silently interpreting them under integer semantics.

## Prove one actual optimization step

The factory's Rust pattern match introduces explicit pair checks. A typed-IR
pass removes a pair guard only when every successful evaluation of its kept
branch requires a checked first/rest projection of that same argument. The
projection still rejects atoms. Facts from strict operands combine; facts from
lazy branches must hold in both branches. The pass keeps the full external ABI
validation and never cancels the required projection.

The report contains the actual rewritten IR, not a separately written ideal
program. Z3 compares the actual original and rewritten expression trees over
the same arbitrary finite environment. A mismatch means different acceptance,
or different output when both accept. Both atom and pair domains have checked
witnesses; their counterexample queries are unsatisfiable. The rewritten IR
also satisfies the independent `p2_conditions` specification.

Actual compilation is recorded separately: source-derived IR produces 65 bytes
without optimization and the canonical 9 bytes with optimization. Rewritten IR
produces 13 bytes without Rue optimization and 9 with it. Optimized Rust,
independently compiled Chialisp, and optimized Rue therefore reproduce the
published bytes and tree hash. This identity is measured from compiled artifacts;
it is not inferred from the SMT result. Rust optimization enables the typed-IR
pass followed by Rue LIR optimization; Rust's unoptimized mode enables neither.

The negative control is deliberately unsafe: a pair-only guard around a
constant result has no required projection. Removing it would accept atoms.
The real optimizer keeps the guard; an explicitly labeled synthetic IR edit
removes it, and the solver finds an atom counterexample. Both guarded VM builds
reject that witness and both edited builds accept it. This control tests the
equivalence checker's ability to distinguish a superficially similar bad rule.

Independent bounded interpreter/VM tests additionally cover nested guards,
strict discarded operands, lazy branches, different arguments, checked
arithmetic, tuple fields, malformed typed environments, and repeated
optimization. These executed tests complement the model proof for this factory.
They do not establish a universal theorem for the optimization algorithm, Rue's
passes, or source-to-CLVM compilation. Cost and diagnostic strings can change;
the equivalence relation covers modeled rejection and successful output only.
It does not turn a resource-limited inconclusive execution into model evidence.

## Remaining trust boundaries

The scalar checks assume successfully decoded canonical typed values. The
structural checks instead model whole raw trees. Neither establishes the ABI
decoder, rustc MIR extraction, SMT translation, Rue optimizer, or CLVM lowering.
Byte semantics are outside the scalar model.
The counter is not a condition-producing puzzle, and its proof does not
establish spend-bundle validity or economic security.

Lean remains an option for future semantics and compiler-preservation work.
The implemented formal mechanism here is SMT/model checking with Z3; the
repository does not claim a completed Lean proof of the compiler.
