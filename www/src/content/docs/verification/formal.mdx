The formal companion works on typed scalar expressions in the actual
source-derived IR. Independently written specifications describe the intended
counter policy. Z3 looks for a violating input; its statuses and replay
evidence are recorded rather than translated into a blanket security claim.

<FormalEvidence />

## What is specified

For `bounded-counter`, the range obligation says that every successful result
is between 1 and 1,000 and equals the input plus one. The acceptance obligation
says that, for a successfully decoded typed `u64`, execution succeeds exactly
when input is below 1,000.

The report includes source, original/mutant IR, specification, and SMT query
hashes so the model and obligations can be tied to the specific compiled
fixture. The site verifies those files before building. A satisfying input demonstrates nonvacuity: the
property is not “proved” merely because every input rejects. That witness is
replayed in native Rust and both CLVM optimization modes.

## Show that a broken guard is caught

The mutation removes only the outer `counter < 1000` assertion and retains
checked increment. The solver must produce a counterexample to the range
specification. The original native function and both original CLVM programs
must reject it; both mutated CLVM programs must accept the now-out-of-policy
result.

This connects a model-level finding to executed artifacts. Witness replay is
still test evidence, not a universal compiler-preservation theorem.

Replay rejection has typed failure evidence. The scalar assertion witness must
report `{kind: "program", code: "raise"}`; a matching diagnostic string does not
count. Tree projections can reject with other program codes. A cost, allocator
or VM stack limit is a resource failure, and serialization/internal errors are
infrastructure failures. Both categories abort proof replay instead of becoming
rejection witnesses. The current report gates reject missing, unknown or
inconsistent metadata, including inside mutation and optimization controls.

The shared classifier and wire protocol, plus the replay gate helpers, are
hashed evidence inputs. These checks bind recorded executions to their failure
interpretation; they do not prove VM semantics or resource equivalence.

## A separate structural tree model

The [p2_conditions factory](/chialisp-oxide/tutorials/p2-conditions/) adds a
separate model over arbitrary finite atom/pair trees. Atom contents are byte
sequences, rather than integers; leading zeros and improper tails are preserved.
The independent specification requires acceptance exactly for pair environments
and output `(1 . first(environment))`. Its domains include both atoms and pairs,
with nonvacuity checks and mutation counterexamples replayed in the VM.

<StructuralEvidence />

```sh
python3 scripts/check-tree-proofs.py --output corpus/tree-proofs.json
```

The [structural report](/chialisp-oxide/reports/tree-proofs.json) includes its
source-derived IR, independent specification, SMT queries, and replay evidence.
This is an IR-model proof, not a theorem about all compiled Rust. Recursive
data in this model is separate from the frontend's
[recursive Rust call support](/chialisp-oxide/tutorials/recursive-trees/).
All current SMT model APIs reject all version-4 runtime programs, including unused
functions and runtime nodes in dead branches. Finite VM replay does not prove
termination; resource failures abort replay rather than count as rejection.
Restricted owned pair construction is available in the frontend, while general
allocation and program evaluation remain unsupported. The scalar verifier rejects
tree expressions, including expressions in unchosen branches, instead of
silently interpreting them under integer semantics.

## Prove one actual optimization step

The factory's Rust pattern match introduces explicit pair checks. A typed-IR
pass removes a pair guard only when every successful evaluation of its kept
branch requires a checked first/rest projection of that same argument. The
projection still rejects atoms. Facts from strict operands combine; facts from
lazy branches must hold in both branches. The pass keeps the full external ABI
validation and never cancels the required projection.

The report contains the actual rewritten IR, not a separately written ideal
program. Z3 compares the actual original and rewritten expression trees over
the same arbitrary finite environment. A mismatch means different acceptance,
or different output when both accept. Both atom and pair domains have checked
witnesses; their counterexample queries are unsatisfiable. The rewritten IR
also satisfies the independent `p2_conditions` specification.

Actual compilation is recorded separately: source-derived IR produces 65 bytes
without optimization and the canonical 9 bytes with optimization. Rewritten IR
produces 13 bytes without Rue optimization and 9 with it. Optimized Rust,
independently compiled Chialisp, and optimized Rue therefore reproduce the
published bytes and tree hash. This identity is measured from compiled artifacts;
it is not inferred from the SMT result. Rust optimization enables checked
constants, forward success facts, constants again, branch-local integer intervals,
legacy tree guards, bounded helper inlining, runtime frame elision, the lazy
canonical-integer decoder, Rue LIR and static pair codegen. The frame
stage has no effect on this runtime-free factory; unoptimized mode skips these optional stages. This
model proof concerns the stated guard rewrite; it does not prove every new pass.

The negative control is deliberately unsafe: a pair-only guard around a
constant result has no required projection. Removing it would accept atoms.
The real optimizer keeps the guard; an explicitly labeled synthetic IR edit
removes it, and the solver finds an atom counterexample. Both guarded VM builds
reject that witness and both edited builds accept it. This control tests the
equivalence checker's ability to distinguish a superficially similar bad rule.

Independent bounded interpreter/VM tests additionally cover nested guards,
strict discarded operands, lazy branches, different arguments, checked
arithmetic, tuple fields, malformed typed environments, and repeated
optimization. These executed tests complement the model proof for this factory.
They do not establish a universal theorem for the optimization algorithm, Rue's
passes, or source-to-CLVM compilation. Cost and diagnostic strings can change;
the equivalence relation covers modeled rejection and successful output only.

## A separate canonical-integer law

The [integer decoder model](/chialisp-oxide/reference/optimization/#decode-canonical-integers-without-repeating-the-body)
checks an encoding law over arbitrary finite byte sequences: minimal signed
atoms are nil or lie in unsigned lexicographic `[0080, ff80)`. Its retained
14 baseline queries and nine mutation queries are distinct from the
source-derived factory and byte-policy models above. The decoder-source hashes
are metadata freshness only; no source-to-model translation or native/VM bridge
is claimed. Finite VM tests exercise the implementation separately.

The [exact report](/chialisp-oxide/reports/integer-canonicality-proof.json)
retains solver/version metadata, full queries, statuses and scope. Documentation
builds inspect that record offline; compiler verification reruns Z3. This law
does not prove actual CLVM opcodes, complete ABI checking, numeric width,
compiler preservation or transaction costs.
It does not turn a resource-limited inconclusive execution into model evidence.

## Integer masks and strict Boolean operations

The scalar IR model also handles fixed-width `&`, `|` and `^`. Such programs
use bitvector input symbols with exact signed/unsigned integer interpretations.
Every value in each declared integer type has one input word; this adds no
axiom or sampling restriction. Operations preserve typed word representations,
while checked arithmetic remains mathematical and converts exactly at a later
bitwise use. Frontend
integer `!` uses XOR with the width maximum for unsigned values or -1 for signed
values. Boolean `&`/`|`/`^` keep both operand success conditions; their strict
execution differs from `&&` and `||`.

Independent identity specifications and deliberately wrong masks exercise the
model across supported widths. Mixed arithmetic and domain-extrema controls
check the representation boundary; unknown or timed-out queries still produce
no proof. Counterexamples are replayed in the VM with
optimization off and on. Separate actual Cargo frontend and IR execution tests
check native results, input encoding and failure order. These test suites are
not additions to the published inequality policy's eight retained models.

```sh
cargo test --locked -p chialisp-oxide-verifier --test bitwise
```

No claim here establishes Rust/MIR/IR/CLVM preservation, hashing support or a
cryptographic theorem. Read [bit masks and evaluation order](/chialisp-oxide/reference/supported-rust/#bit-masks-and-evaluation-order)
for the source behavior and remaining policy obligations.

## A whole-environment byte policy

The [byte-policy proof guide](/chialisp-oxide/verification/byte-proofs/) starts
from the actual annotated Cargo `atom-not-equal` export. Its independent
specification accepts exactly a proper two-atom argument list and returns
canonical Boolean inequality. Atoms are sequences of 8-bit values: nil,
nonempty zero bytes, padding and invalid UTF-8 are distinct. Acceptance is
specified over the entire environment, including its exact empty final tail.

Eight models cover the original, five actual Cargo source controls and two
explicitly synthetic ABI edits. Operator inversion, self-comparison and two
constant policies are refuted; operand reversal is a positive equivalence
control. The synthetic controls widen the environment or narrow operand
lengths. Separate ABI/acceptance/true/false nonvacuity obligations prevent
vacuous conclusions. Stable witnesses are checked by the solver after solving
the unbounded queries, rather than replacing those queries with a finite set.

Both optimization modes of each model are retained and selected witnesses
execute their exact serialized programs. Original-policy witnesses also run
through all five original Chialisp/Rust/Rue builds; native replays invoke the
actual Cargo exports. The [report](/chialisp-oxide/reports/byte-proofs.json),
IR, specification and SMT obligations are linked from the guide. This is an
IR-model result plus finite execution evidence, distinct from the earlier
hand-authored byte-IR regressions. It establishes neither compiler preservation
nor complete Chialisp/library parity.

## Remaining trust boundaries

The scalar checks assume successfully decoded canonical typed values. The
structural checks model whole trees, and the byte-policy model explicitly
models its strict decoder. Modeling a decoder does not prove its emitted
implementation. None establishes rustc MIR extraction, SMT translation,
primitive bridging, Rue optimization or CLVM lowering. Byte semantics remain
outside the scalar model. The installed pinned compiler and matching
unmodified standard library are trusted. Target configuration and actual loaded
primitive-owner locations must use that installation, without authenticating
its bytes. See [compiler trust](/chialisp-oxide/reference/compiler-trust/) and the
[toolchain trust notes](https://github.com/judeallred/chialisp-oxide/blob/main/docs/toolchain-trust.md).
The counter is not a condition-producing puzzle, and its proof does not
establish spend-bundle validity or economic security.

## Separate Lean algorithm theorems

The recursive [prefix adapter](/chialisp-oxide/tutorials/prefix-list/) and
[last-element adapter](/chialisp-oxide/tutorials/last-list-element/) have a
separate manually authored Lean model. Its theorems concern all finite trees
under that model, while the bridge to actual compiled programs covers only the
recorded inputs. Neither layer proves Rust/MIR/IR/CLVM preservation.

<AlgorithmEvidence />

With the pinned Lean 4.35.0 toolchain on `PATH`, reproduce the full check:

```sh
python3 experiments/tree-theorems/check-model.py --self-test --replay-vm \
  --output experiments/tree-theorems/results.json
```

The site uses a separate command that requires no Lean installation:

```sh
python3 experiments/tree-theorems/check-model.py --check-recorded --self-test
```

This second command checks freshness, recorded theorem names/axioms, source and
artifact hashes, bridge coverage and the scope of the record. It does not rerun
the kernel or the VM. Compiler CI performs the real kernel checks and replays.
The IR-derived SMT obligations and manual Lean algorithm theorems remain
distinct; the repository does not claim a completed Lean proof of the compiler.
