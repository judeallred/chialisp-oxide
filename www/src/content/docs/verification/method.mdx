Every validated fixture is compared through independently executed paths. The
goal is to make a wrong assumption fail visibly at more than one boundary.
No passing suite establishes a general absence of vulnerabilities.

The report includes exact local source dependencies explicitly declared by
each fixture manifest. Site checks compare their paths, source text, and
SHA-256 values against the repository, alongside the entrypoint and reference.
Both validation and proof reports also record the package, library, export
mapping, and hashed local inputs declared in `puzzles/authoring.json`. The site
requires these records to agree and match current files. This prevents a
changed SDK or Cargo input from leaving stale displayed evidence; it is not an
automatically discovered complete transitive dependency graph.

## Native Rust, Chialisp, and Rue

The Rust fixtures are annotated exports of the real `chialisp-oxide-puzzles` Cargo
library. Validation extracts that package once and its native oracle links the
same library. The native solution decoder
enforces the fixture ABI; rejection is compared as carefully as successful
output. Chialisp is compiled by Chia Network's Rust compiler, independently of
chialisp-oxide's lowering code. Authored `mod` references enforce the strict
teaching-fixture ABI. The canonical closed expressions instead use the raw
expression compilation stage and explicitly ignore their environment in both
the Rust export, original Chialisp, and authored Rue translation.

The canonical `p2_conditions` factory uses an explicitly raw whole-tree
environment in Rust. Its exact original module and Rue source accept arbitrary
pair tails and payloads. The host codec copies atom bytes without numeric
interpretation; two iterative traversals avoid using native call-stack depth
as the input-data limit. The default typed fixtures keep their exact ABI.

Rue is separately compiled from each recorded `puzzle.rue` by its pinned
frontend, with LIR optimization off and on. Its standard condition types and
explicit environment guards are real source, not Rust-generated Rue text or
wrapped CLVM. Rue’s unbounded `Int` needs explicit canonical `u64` checks in
these comparison policies. Those guards remain visible in the source.

The report separates {format(totals.originalExamples)} original teaching
comparisons from {format(totals.canonicalPorts)} canonical tutorial program
ports, all with explicit provenance. The {format(totals.canonicalPuzzlePorts)}
canonical module ports retain applicable factory, published-identity or
complete-spend evidence. The {format(totals.canonicalHelperPorts)} published helper adapters
invoke exact source spans through explicit module wrappers; those comparisons
do not claim a canonical standalone module hash. These ports do not complete a tutorial
page, source library or protocol migration.
Familiar condition codes in a teaching
fixture do not make it a canonical protocol module.

## Optimized and unoptimized CLVM

The Rust source compiles through typed MIR into both backend modes. Each named
input compares native output/rejection against unoptimized Rust CLVM, optimized
Rust CLVM, independently compiled Chialisp CLVM, and Rue source compiled with
optimization off/on. The scalar examples also
have generated sweeps around their bounds.

Rust's enabled pipeline runs checked constants, forward success facts, constants
again, branch-local integer intervals, legacy tree guards, bounded helper
inlining, runtime frame elision, the lazy canonical-integer decoder, Rue LIR and static pair codegen; its disabled pipeline skips these optional stages.
Frame elision applies only to runtime lowering. Rue source off/on controls
only its LIR optimizer. The report records this distinction in
`optimization_pipeline`, alongside the historical `optimize_lir` build flag.
The comparison contract covers rejection and exact returned bytes, while costs
and error strings may differ.

Runtime frame elision forwards already-bound values and literals without new
slots, lowers operations that consume an operand once directly, and returns a
tail binding's initializer directly. Fallible multi-operand computations still
execute once in source order. Forward facts describe a continuation only after
the relevant operation returns. The older backward pair-guard pass continues to
leave runtime IR unchanged: moving an earlier rejection past a diverging call
would change behavior. See [optimization](/chialisp-oxide/reference/optimization/).
Executed regressions cover these boundaries; current model proofs reject runtime
IR and do not prove this lowering correct for arbitrary programs.

The typed IR pass also has an independently implemented bounded interpreter and
tree/expression matrix. It checks original and rewritten behavior, repeated
optimization, lazy branches, discarded tuple/scalar failures, malformed scalar
encodings, and multiple argument identities against actual CLVM executions.
The highest argument-mask bit and invalid public inputs have separate analysis
controls. The factory's structural model checks the source and rewritten IR
against its independent specification and their equivalence; that is narrower
than proving the pass correct for all programs.

The report records serialized bytes, disassembly, tree hash, byte size, and
per-case execution cost. A rejected run may have no returned cost; it must not
be displayed as a zero-cost execution. VM execution cost is separate from
condition costs and total transaction admission cost.

## A VM error is not automatically policy rejection

The shared failure protocol is `clvmr-0.21.0/v1`. The Rust classifier matches the
actual VM error variant; the site and Python checks use the same exhaustive
`failure-protocol.json` table. Diagnostic strings are display text, not evidence
for a failure category.

A `program` failure produces `rejected`. Examples include `raise`,
`path_into_atom` and `division_by_zero`; this means a VM-semantic failure, not
necessarily an intended policy assertion. `resource` failures such as
`cost_exceeded` or VM stack limits, and `infrastructure` failures such as
serialization or internal errors, produce `inconclusive`.

A failed execution must carry a valid `{kind, code}` pair. A successful one
must omit failure metadata. Current validation requires conclusive runs:
unknown codes, missing metadata, forged categories and inconclusive execution
fail the gate. Checking only the returned status or matching a word in an error
message is insufficient. Native policy outcomes remain separate from this VM
protocol.

The proof replay tools abort on resource or infrastructure errors. Their
rejection evidence must identify a program failure; the counter's assertion
witness specifically requires code `raise`. This prevents an exhausted cost
budget from masquerading as a caught attack. It does not establish equal
resource behavior between native Rust, the IR model and CLVM.

## Actual coin-set validation

The report contains {format(totals.coinPuzzles)} condition-producing examples
and {format(totals.pureFunctions)} pure-function examples, plus
{format(totals.programFactories)} program factory and
{format(totals.protocolComponents)} protocol component. Ordinary ledger scenarios belong to coin puzzles. The same scenarios run separately with Rust, Chialisp, and Rue reveals;
{format(totals.ledger)} scenario definitions produce {format(totals.ledgerRuns)} ledger scenario runs. A group can submit several bundles, so this is not a transaction count. They verify
coin-state transitions, exact recipients/totals, signatures, input amount
assertions, locks, repeated spends, and rollback where relevant.

The report records {format(totals.consensusRejections)} exact consensus rejection
checks across the three languages. Each negative observation has stage
`consensus` and the expected typed `chia-consensus` error code. Missing or partial
signatures are submitted as actual spend bundles and must produce
`BadAggregateSignature`; the recovery group separately checks
`AssertSecondsAbsoluteFailed` and `BadAggregateSignature`. A wrong code, an
unrelated consensus error, or an SDK `MissingKey` preflight failure cannot count
as that expected rejection. Positive scenarios have an empty rejection list.

These observations use the separate `chia-consensus-0.36.1/v1` protocol and the
simulator's `clvmr 0.16.2` stack. They are not primary `clvmr 0.21.0` program
failures. The closed scenario/code table, its hashes and the Python/Node gates
keep these two evidence boundaries distinct. Each coin fixture must include
its complete ordered scenario list; removing the same scenario from every
language is also a failed gate. Codes are specific to the policy: the boolean
gate has no `ASSERT_MY_AMOUNT`. An input of 999 mojos cannot fund its output
of 1,000 mojos and fails conservation with `MintingCoin`. An input of 1,001
mojos succeeds, creates the same child of 1,000 mojos and leaves 1 mojo as an
implicit fee. These are separately named
scenarios; the amount-asserting fixtures instead require
`AssertMyAmountFailed` when their exact input amount differs.

The [pay-to-singleton component](/chialisp-oxide/tutorials/p2-singleton/)
embeds its dedicated canonical-counterpart observations separately: five
compiler builds, 110 actual submissions, 15 accepted and 95 exact typed
consensus rejections with complete rollback. They use the scoped
`chia-consensus-0.36.1/p2-singleton-v1` protocol and do not increase the ordinary
scenario-group totals above. The canonical singleton top layer and signed
StandardLayer are host counterparts, not Rust ports. A real Eve spend and
one subsequent lineage transition do not establish a full singleton lifecycle.

Separate simulator infrastructure regressions exercise overspending,
announcements, and message binding. Do not infer that every puzzle report
contains every infrastructure scenario: each report lists its own checks.

## Mutation and formal evidence

A check is more persuasive when a deliberately broken policy fails it. Guard
removal is modeled and replayed for the counter; the earlier backend experiment
also contains mutation controls. The structural factory model independently
requires pair-only acceptance and exact quote construction; deliberate atom
acceptance and a wrong quote opcode must produce replayable counterexamples.
Model proofs and their assumptions are
[reported separately](/chialisp-oxide/verification/formal/) from finite
differential and simulator evidence.

Raw-tree review exposed two additional Rue optimizer discrepancies:
[pair reconstruction could drop required projection failures](https://github.com/xch-dev/rue/issues/110),
and [quoted execution could replace an explicit nil environment with outer data](https://github.com/xch-dev/rue/issues/111).
Both are fixed in this checkout, with test-first reproductions and standalone
upstream patches. The regressions compare exact outputs and rejection with
optimization off/on. They illustrate why a source/IR-model proof and optimizer
preservation remain separate obligations.

Bitwise review found a separate failure-order discrepancy:
[nested integer reductions could move validation past a recursive operand](https://github.com/xch-dev/rue/issues/112).
A pair supplied to a Rue `Int` entrypoint changed from an immediate
`invalid_op_arg` to resource exhaustion after optimization. The fix retains the
inner reduction. Tests preserve the opposite evaluation-order control, valid
atom inputs and explicit type guards. No mismatch was demonstrated on well-typed
operands; the Rust strict ABI rejects the malformed pair before policy execution.

A separate [canonical Boolean value discrepancy](https://github.com/xch-dev/rue/issues/113)
affects well-typed integer inputs. For input `2`, `value != 0` returned canonical
true without optimization but atom `2` after optimization; `(value != 0) == true`
then changed from true to false. The fix preserves Boolean value normalization
while retaining condition-only truthiness simplification. Source and public-LIR
regressions compare exact bytes, tuple fields, nested Boolean use and required
failures. These are concrete counterexamples and regression controls, not a
universal optimizer-preservation proof.

## What remains to establish

Compiler preservation, decoder correctness, optimizer correctness, broad
protocol migration, economic invariants, target-independent Rust expansion,
and production key management all require further work. Canonical protocols
also commit to module hashes: behavioral agreement does not make different
bytecode a compatible replacement.
