## Successful execution gives useful facts

Consider this sequence over an immutable raw tree:

```text
first(value)
if is_pair(value) { use_pair(value) } else { reject }
```

If `first(value)` returned, `value` must be a pair. The later shape test adds
no information. Our forward analysis records that fact at the continuation
after the projection. It tracks argument and lexical-binding identities, and
keeps only facts valid on every successful incoming branch. A rejecting branch
has no successful continuation. A callee starts a fresh scope.

The direction matters:

```text
if is_pair(value) { spin_forever(); first(value) } else { reject }
```

Here an atom must reject before the call. A later projection cannot justify
removing the earlier guard. The older backward guard pass remains disabled for
runtime programs; the new analysis never uses a future operation to establish
a fact in the past. No termination summaries are assumed for calls.

These are optimizer facts over already validated typed IR. They do not invent
new Rust source types or bypass rustc. Checked Tree-to-Atom casts retain their
IR types; exact construction can make a backend guard redundant while the
constructed payload still executes once.

The ABI gives `counter` its complete `u64` range. After the assertion returns,
the successful branch narrows that range to `0..=999`, so adding one stays in

`1000 - first_amount` safe on that continuation.

The source-derived IR can contain a discarded checked-arithmetic tuple followed
by the same arithmetic again. The current interval pass removes only that
discarded repeated Add/Sub initializer when every operand and the operation
are proven total. The final operation remains checked. Neither the source's
integer type nor the input ABI becomes narrower or unchecked.

Bounds belong to immutable argument and local identities, stay local to each
function, and merge conservatively across successful branches. Calls, SHA and
raw-tree projections gain no totality summary. An earlier failure cannot move
past a call that may diverge. Bounded analysis work, type checks and explicit
overflow tests remain part of the implementation; budget exhaustion skips this
optional pass.

## Decode canonical integers without repeating the body

Integer decoding still runs in this order: atom shape, byte-length cap,
canonical signed encoding, declared numeric range, then the function body.
Optimization replaces repeated substring branches with this encoding law:

```text
minimal signed atom = nil OR (0080 <= unsigned-byte-lexicographic atom < ff80)
```

Nil is the canonical zero and has its own lazy fast path. For other atoms,
`0080` includes the necessary sign byte of positive 128; `ff80` excludes the
redundant sign byte of negative 128. The lower bound must be inclusive:
using `atom > 007f` would wrongly admit `007f00`. The numeric range check still
rejects an otherwise canonical value outside the selected Rust integer type.

The previous decoder placed the continuation in five success branches. The
new decoder uses two, retaining a cheap nil branch and ordered byte bounds.
Finite tests execute every zero-, one- and two-byte atom, longer sign-extension
boundaries, every supported signed/unsigned integer width, malformed argument
shapes, and failures before a divergent body in both compiler modes.

## Fold constants and avoid unnecessary frames

Checked constant folding can turn `2 + 3` into `5` before generic integer checks
are emitted. Overflow remains a failure. An unused total match discriminant can
disappear; an unused call, SHA computation or checked projection still runs.
Only a selected branch of an `if` executes.

Runtime lowering forwards total argument, local and literal aliases without
building another continuation frame. It resolves lexical identities when the
final consumer's scope is known, accounting for intervening physical frames.
Other operands keep ordered, once-only bindings. Static pair code generation
can quote constructed data; it cannot quote away executable children.

## Remove small helper calls safely

Calling a helper has a real cost: its arguments and function table become a new
CLVM environment. The optimizer now inlines small helpers with no further calls,
and can replace an entry that only forwards its arguments with the callee's
body. It then removes unreachable function-table entries and renumbers the
remaining calls. Recursive functions keep their calls.

Inlining preserves Rust's strict evaluation. Every argument becomes an ordered
lexical binding, including an unused argument that rejects, overflows, hashes
or diverges. Callee locals receive fresh identities so they cannot capture a
caller binding. Neither helper names nor SDK names grant special behavior.

Expansion is optional and bounded. The pass checks copy work, literal bytes,
expression depth and continuation-frame growth before accepting a rewrite.
If the candidate hits an existing lowering budget, compilation retries the
previous optimized program. Only typed compiler-limit failures trigger this
retry. Type errors and other compiler errors remain errors. Serialization also
retains the runtime evaluation-order boundary.

Public `optimize()` results can be serialized and compiled again. If deleting the
last runtime binding would expose a possibly failing expression to the legacy
evaluation order, it keeps the original runtime program. A closed whitelist of
total typed results still permits safe reductions. Every constructor and branch
child must qualify; a discarded tuple field can still fail. Ordinary compilation
pins the original evaluation mode separately and keeps its optimized plan.

These limits also exercise the compiler itself. Rue code generation now uses
explicit worklists so small output programs do not overflow a default-sized
native thread stack. The regression and fix are reported in
[Rue issue #114](https://github.com/xch-dev/rue/issues/114). This robustness fix
preserves emitted CLVM bytes; the VM savings above come from the optimizer.

The enabled pipeline is:

```text
validated typed IR
  → checked constants
  → forward execution-success facts
  → checked constants again
  → branch-local integer intervals
  → legacy tree guards (runtime programs unchanged)
  → bounded helper inlining and unreachable-function removal
  → runtime frame elision
  → guarded immutable projection forwarding
  → lazy canonical-integer decoder
  → Rue LIR optimization
  → static pair code generation
```

The recorded eleven-stage metadata retains the forwarding stage name; the
reviewed runtime-composition profile binds the exact combined implementation.
Known-atom facts and compact unary layouts are lowering details within that
implementation, not new Rust source types. Branch-local projection and atom
facts apply to every preflighted table body, including typed `Cons`/Pair bodies.
Compact unary layouts remain disabled for programs with Pair capability,
including an unused Pair-bearing function signature; their call frames stay
proper lists.

`--no-optimize` skips these optional stages. ABI decoding and fixed-width checked
semantics remain active. Every rewritten IR program is validated. An iterative
preflight scans all bodies before the new recursive analyses; deeper programs
follow the previous compiler route. Work, literal-copy and lowering budgets
remain explicit compiler resource limits.

## Check what the savings preserve

The retained transition binds the old signed report, all raw source IR and
unoptimized artifacts. Fresh compilation and VM replay check the new optimized
artifacts. The report also compares actual native Rust, independent Chialisp and
Rue source, generated adversarial trees, and separate ledger scenarios.

Regressions exercise malformed ABI values, padded atoms, lexical alias rebasing,
arithmetic overflow, lazy branches, strict SHA and projection-before-divergence.
Password instances independently reconstruct currying and changed coin IDs;
an optimization cannot pass by rewriting the recorded expected outputs.

Cost limits can change an observation from inconclusive to completed as work
decreases. Those observations stay in the resource-control section and add no
ordinary test or policy-rejection credit. Model proofs for particular IR rules
remain distinct from finite tests of these passes. There is no general
compiler-preservation proof here.
